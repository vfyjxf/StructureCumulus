# 一个设计问题的完整说明：判定与登记分开之后，如何确认世界没有变

这份文档从头解释背景、术语、问题、四个具体场景和可选处理方式，供阅读理解或翻译使用。所有标识符保持原样，不做翻译。

## 一、这个项目在做什么

这是一个 Minecraft 模组内核，负责一件事：判断某一片方块是否构成了蓝图描述的结构，如果可以，就把这片方块的占用关系登记下来，让其他玩家或同一玩家的其他建筑不能再占用。

判定与登记被拆成两个入口。`check` 只读，可以被预览、指令、自动巡查反复调用；`settle` 是唯一会写入的入口，只在结构真正建成时调用一次。拆分的理由是：如果只有一次调用，那么每次预览都会在账本里留下真实记录，预览本身就把地占了。

## 二、术语表

| 术语 | 标识符 | 意思 | 为什么需要 |
| --- | --- | --- | --- |
| 蓝图 | `Blueprint` | 结构模板：外形范围、每个舱位要求的方块、锚点与朝向 | 判定需要一个参照物 |
| 落点 | `Siting` | 蓝图在世界中的具体位置与朝向 | 同一张蓝图可以放在任意位置 |
| 舱位 | `Bay` | 蓝图内一块受检区域，例如开口、外壳的某一面、内部空腔 | 检查与占用都以区域为单位 |
| 主体 | `OccupantRef` | 判定过程中实际绑定到的东西，例如一扇门、一个方块实体 | 有些舱位的占用范围取决于实际绑定到什么 |
| 绑定 | `BayBinding` | 记录某个舱位绑定到了哪些主体 | 占用的格子由绑定推导得出 |
| 声明 | `ClaimRow` | 一条记录：某个世界里的某个格子归某个舱位的某个占用者 | 账本的基本单位 |
| 共享与独占 | `Sharing` | 独占表示该格只允许此占用者使用，共享表示允许他人同时使用 | 冲突判定需要区分 |
| 账本 | `ClaimLedger` | 所有声明的持久化存储，按世界分开，句柄绑定单一世界 | 跨存档保存占用关系 |
| 冻结副本 | 快照 | 某一瞬间对一片方块的只读拍摄结果 | 判定只读副本，不读活世界，保证同一次判定看到的世界一致 |
| 租约 | `SnapshotLease` | 持有冻结副本的句柄，同时记录该区域后续的方块改动；关闭即释放副本 | 判定与登记之间副本必须存活 |
| 世界代数 | `mapGeneration` | 世界被整体替换时递增的计数 | 区分“世界换了”与“世界内变了” |
| 捕获标识 | `SnapshotId` | 世界加捕获版本组成的标识 | 确认比较的是同一份副本 |
| 改动计数 | `changeCount` | 判定以来监视区域内方块被标记改动的次数 | 确认区域没有被改动 |
| 请求序号 | `Ticket` | 宿主分配给一次提交的递增序号 | 同一槽位内合并新提交 |
| 槽位 | `CheckKey` | 由世界与占用者组成的队列位置，同一位置同时只处理一个任务 | 限制并发并合并重复提交 |
| 计划 | `ClaimPlan` | 判定通过后留下的产物，记录每个舱位的绑定以及判定时读到的账本修订号，不含任何格子记录 | 提供预览，并为登记提供输入 |
| 修订号 | `ledgerRevision` | 账本每写一次递增的计数 | 登记时确认账本没有在判定后被他人修改 |
| 判定 | `check` | 只读入口，返回六种结果之一 | 可被任意频繁调用 |
| 登记 | `settle` | 唯一写入入口，自己用纯函数从请求与绑定推导出要写的格子 | 只有真正建造时才调用 |

判定入口的签名是 `check(MatchRequest request, Supplier<SnapshotInfo> live)`，登记入口的签名是 `settle(MatchRequest request, ClaimPlan plan, Supplier<SnapshotInfo> live)`。`MatchRequest` 携带九项内容，其中一项是 `SnapshotInfo`，还有一项是 `SnapshotLease`；它的世界由 `SnapshotInfo` 派生。

判定返回 `MatchResult`，这是一个封闭的六分支结果类型：`Admitted`（通过但未登记，携带计划与账本修订号）、`Formed`（已登记）、`Dropped`（前置条件失效，不发布也不写入）、`Failed`（不匹配或有冲突）、`Undecided`（无法得出结论）、`Deferred`（延后重试）。

## 三、两步流程的完整时序

1. 宿主为某个 `(world, owner)` 槽位发起一次提交，分配一个 `Ticket`，拍摄一份冻结副本并建立租约。
2. `check` 在这份副本上逐舱位比对。通过时它做三件事：记录每个舱位绑定到哪些主体，读出账本当前修订号，保留租约。
3. `check` 返回 `Admitted`，携带 `ClaimPlan` 与修订号。
4. 调用方决定是否登记。登记时宿主调用 `submitForm(admitted)`，把租约移入登记请求。
5. `settle` 重新核对若干事实，然后用纯函数从请求与绑定推导出要写的格子，最后对账本做一次原子写入。

第 5 步的“重新核对”就是本文讨论的对象。

## 四、登记前为什么需要核对

判定是在某一瞬间的世界状态上做出的。登记发生在之后，可能隔一瞬，也可能隔几分钟。这期间可能发生：世界被重载或替换；有人改动了那片方块；冻结副本被释放；同一玩家发起了新的判定。

核对的目的只有一个：确认“我现在要登记的东西，仍然是当时判过的那个情形”。设计把这项核对压缩成一个值对象 `SnapshotInfo`，内含五项事实，比较方法 `agreesWith` 一次判完，返回 `CURRENT`、`CHANGED` 或 `SUPERSEDED`。后两者都产生 `Dropped`，不发布结论，也不写入任何格子。

| 字段 | 记录的事实 | 不成立的结果 |
| --- | --- | --- |
| `mapGeneration` | 世界仍是同一个 | `SUPERSEDED` |
| `request`，类型为 `Ticket` | 本次提交仍占据槽位 | `SUPERSEDED` |
| `snapshot`，类型为 `SnapshotId` | 仍是判定时那份副本 | `SUPERSEDED` |
| `changeCount` | 判定以来监视区域未被改动 | `CHANGED` |
| `held` | 租约仍然打开 | `SUPERSEDED` |

其中四项描述世界与副本的状态，`Ticket` 一项描述调度队列的状态。

判定与登记是同一次调用时，两类状态始终同步：一次任务对应一次调用，只有被新任务顶掉才会失效。拆成两次调用后两类状态分离，世界可以毫无变化而请求序号已经前进。

## 五、四个具体场景

### 场景一：预览使待登记的清单失效

玩家瞄准一处，预览调用 `check`，通过，得到 `Admitted` 并持有租约，此时槽位序号为 7。准星轻微移动再移回，预览再次调用 `check`，同一槽位序号变为 8。玩家点击建造，宿主调用 `submitForm` 发起登记，`settle` 用请求携带的 `SnapshotInfo`（序号 7）与当前状态（序号 8）比较，序号不相等，返回 `Dropped(REQUEST_SUPERSEDED)`。

结果是结构已经建成却登记失败，而且只要玩家的准星在动，预览就一直刷新序号，重试会持续失败。

### 场景二：`live` 被实现为重新拍摄

`check` 与 `settle` 都接收一个 `Supplier<SnapshotInfo> live`。规格对它的全部说明是“结尾读取一次”，没有规定它必须返回什么。宿主按字面把它理解成“现在重新拍一份副本再报告状态”，此时 `snapshot` 字段（`SnapshotId`）与请求携带的那份永不相等，`settle` 永远返回 `Dropped`，`check` 自身也会返回 `Dropped`。

这是当前规格里最直接的一处空缺。按字面实现，这套核对无法通过任何一次调用。

### 场景三：已出结论的请求的租约被队列关闭

队列规则允许在收尾阶段关闭被顶掉的提交所持有的租约。一个提交已经返回 `Admitted`、正在等待登记时，它的租约同样会被关闭，`held` 变为假，登记被丢弃，且结果中不包含具体原因。

### 场景四：登记成功后租约无人释放

`Admitted` 持有一个子租约，`Formed` 持有另一个。示例代码在成功路径只关闭 `Formed`，`Admitted` 的子租约连同改动计数一直保留，造成资源与监视长期占用；调用方若两处都关闭，则重复释放。

## 六、问题的形成

五项检查混合了两类事实。前三项中的世界与副本、改动计数、租约状态，回答“我看的那个东西现在是否原样”；`Ticket` 回答“这次提交在队列里是否仍然有效”。

在一次性调用的形状里，这两类事实始终一致，所以放进同一个比较方法没有代价。拆成两次调用后，`Ticket` 的语义发生偏移：任何一次新的判定（包括预览）都会推进槽位序号，从而使已通过、待登记的判定失效；而登记本身是否推进序号，规格没有写明。实现按“推进”理解时，所有登记都会被丢弃；按“不推进”理解时，`Ticket` 在登记这一步的含义无法解释。

## 七、四种处理方式

**五项继续一起比较，并规定 `submitForm` 沿用原 `Ticket`。** 改动最小。预览导致的问题仍然存在；要消除它必须允许预览不占用槽位，而预览同样需要租约与改动计数，只能另建一条不排队的路径，机制数量翻倍。

**按事实类别拆分：发布结论时比较五项，`settle` 只比较 `mapGeneration`、`snapshot`、`changeCount`、`held`。** `Ticket` 从未承担保护世界的职责，承担这一职责的是 `changeCount`，且它的判据故意严格，监视区域内任何一格变动都会使整次判定作废。取消登记时的序号比较不会放过任何原本应被拒绝的情形，只会让世界未变、仅预览刷新的正常情形不再被丢弃。副作用是 `ClaimPlan` 的有效期获得明确语义：区域未变动且租约仍打开时计划有效，任何变动立即使其失效。

**登记时重新拍摄一份副本再比较。** 现在拍摄只能说明当前状态，无法说明两次拍摄之间是否发生变动，判断仍然依赖 `changeCount`；同时需要完整重读一遍区域，增加开销而未增加保障。

**让 `submitForm` 递增 `Ticket` 并用新值比较。** 序号比较恒为真，该项检查成为不可达分支，应当删除而不是保留。

## 八、建议

采用第二种，并补三条规则。

`live` 必须返回请求所命名那份捕获的当前状态：同一 `mapGeneration`、同一 `SnapshotId`、当前的 `changeCount`、当前占用槽位的 `Ticket`、以及该租约是否仍然打开；禁止重新拍摄。宿主返回另一份捕获时比较不相等，结果为 `Dropped` 且不写入，失败方向安全。

请求一旦返回 `Admitted`，其租约不再由队列释放。槽位合并只关闭尚未产出结论的提交所持有的租约，已出结论的租约由持有 `Admitted` 的调用方与随后的 `settle` 负责。

一份 `ClaimPlan` 只允许登记一次。`settle` 成功后由它关闭 `Admitted` 持有的子租约，失败路径由调用方关闭，两处各一次。

## 九、需要确认的三点

1. `settle` 的比较是否去掉 `Ticket` 一项，只保留其余四项。
2. 槽位合并是否允许关闭已经返回 `Admitted` 的提交所持有的租约。
3. `settle` 成功后是否由它关闭 `Admitted` 持有的子租约。

## 十、附带的一处未决内容

宿主的提交请求 `CheckRequest` 目前有两个字段与内核模型不一致：`Place` 已经明确为“宿主尚未确定的目标位置”，只在宿主侧使用；`List<Stage>` 仍然存在，而内核的 `MatchRequest` 已经不再携带阶段。后者的归属取决于另一个未决问题：谁在分开的流程里决定一次判定运行在哪个阶段。
