# P1 — blind generation vs `kernel.{base,space,occupant}`

Method: skeleton written from `01-glossary.md`, `05-space.md`, `06-occupants.md` only
(`p1-skeleton.md`, 54 compilation units, `javac` clean), then compared against
`src/kernel/java/dev/vfyjxf/cumulus/kernel/{base,space,occupant}`.
Labels: **(b)** doc states it differently, **(c)** doc never mentions it.

Headline: the three docs describe a *larger and different* U2 than the code has. Doc-declared but
code-absent (not counted as findings, since a generator writes them fine): `Budget`, `Spend`,
`CancelToken`, `Stability`, `Arguments`, `ParameterKey`, `DataView`, `DataKind` (base);
`Locus`, `LocusFrame`, `LocusMap` (space); `TraitKey`, `Trait`, `Traits`, `OccupancySummary`,
`ChunkContent`, `World`, `SnapshotPolicy`, `WorldWindow`, `WorldCapture`, `CaptureRequest`,
`CaptureLimits`, `CaptureResult`, `OccupantResolver`, `ResolveContext`, `NestedView` (occupant).
Conversely `base` holds the whole finding vocabulary that `01-glossary.md` assigns to
`kernel.finding` (`Finding`, `FindingCode`, `FindingBundle`, `FindingId`, `Label`, `LabelRole`,
`Note`, `Severity`, `Suggestion`, `Applicability`, plus `Outcome`, `ReadScope` from `expectation`).

## 1. What I could not write from the docs alone

Ranked by how much generated code would fail to compile or would be wrong.

## 3. Members the docs omit

**`base`**

- `NamespacedId`: `DEFAULT_NAMESPACE = "structurecumulus"`, `text()`, `toString()`; ctor validation
  (`[a-z0-9_.-]+`, `[a-z0-9_./-]+`, no leading/trailing/double slash) — the doc says "validated" and
  nothing more.
- `SourceSpan`: `of`, `length()`, `contains(SourceSpan)`, `contains(int)`; ctor rejects `start < 0`
  and `end < start`.
- `Locus`: extra factory `world(CuboidSet, SourceSpan)`; `LocusFrame.rank()`.
- `Locus`'s nullness contract lives in ctor checks; the doc states it as prose rules L-1/L-2, which
  is enough — but the *other* direction (LOCAL/WORLD may or may not carry a span) is only implied.
- `Finding`/`FindingBundle`: no `filter(...)` (which `01 §K` advertises); instead `ofCode`, `ofSeverity`,
  `plus`, and a private dedup key over `(severity, stage, code, labels, notes)` that `01 §K` never
  describes; `FindingId.NONE == 0` is coded but "NONE means not addressable" is the only doc line.
- `ReadScope`: `(CuboidSet cells, Set<ContextKey<?>> keys, List<EntityWindow> entities)` with
  `none()/withKeys/union/isEmpty` — `01 §E` describes it in words only ("cells, keys and entity
  windows"), and `EntityWindow` is a U2 type it never introduces.
- `Outcome.Found.subjects`, `Outcome.fold` — doc covers this; the code's `fold` takes
  `BiFunction<T, List<OccupantRef>, R>` which the doc does not spell out. (fine)

**`space`**

- `LatticePoint`: `MIN_XZ/MAX_XZ/MIN_Y/MAX_Y` public constants; `toString()`.
- `LatticeKey`: `x()`, `y()`, `z()` unpack accessors, `toString()`.
- `CuboidSet`: `intersect(Cuboid)` and `union(Cuboid)` overloads (the doc says only `subtract` comes
  in both forms), `equals`/`hashCode` are structural over `boxes()`, `containsAll` is implemented as
  `other.subtract(this).isEmpty()`.
- `Orientation`: `then(Orientation)` (composition in the other order, `space/Orientation.java:60`) and
  `id()` (`:131`). The doc defines only `compose`, and warns that order matters — an undocumented
  second order is the worst kind of addition.
- `ChunkGrid`: `ADAPTER_CELL_SIZE = 16`.
- `SectionKey`: exists at all (see §1.6).

**`occupant`** — `SectionSnapshot`, `SectionSnapshot.Builder`, `SectionSnapshot.CellIndex`,
`SectionSlot` (+`Air/Present/Refused`, `readable()`), `OccupantFilter`, `EntityWindow`,
`EntityKey`, `ChangeSet`, `NestedLevelSnapshot`, `WorldView.slot/occupant(OccupantRef)/nested/contentDigest`,
`OccupantSnapshot.hasTrait`, `OccupantDescriptor.of`, `OccupantKind.of`.

## 4. What the docs do cover well

- **The packing (`05 §4.1`).** `LatticeKey` is byte-for-byte the doc's bit layout, and the doc's one
  real warning — `compareTo` must delegate to `LatticePoint`'s `(y,z,x)`, never to `packed` — is
  exactly what the code does, with the same comment. My skeleton got this from the doc alone.
- **`Cuboid` (`05 §4.2`).** Every edge case I coded blind is the code's edge case: empty cuboid is
  legal and `contains` is false, `contains(empty)` is true, `intersects` is false for an empty
  operand, `intersect` returns `null` instead of an empty box, `volume` saturates, no
  `union`/`subtract` on the cuboid.
- **`CuboidSet` (`05 §4.3`).** The four-step canonicalisation (drop empties, cut x then z, merge
  overlapping y only, sort), `of` as the only door, structural equality, and "semantic equality is
  `containsAll` both ways" — all reproduced exactly, including `containsAll` being implemented as
  `other.subtract(this).isEmpty()`.
- **The 48-element group (`05 §4.5`, `P3`).** The ordinal formula
  `(turn*6 + tilt)*2 + parity` is the code's index, `IDENTITY == 0`, `all()` ascending,
  `Tilt.up()` images (`LEVEL→UP, PITCH_UP→SOUTH, PITCH_DOWN→NORTH, ROLL_LEFT→WEST, ROLL_RIGHT→EAST, INVERTED→DOWN`)
  are exactly the doc's table, and the doc's 72-names/48-elements warning is answered by the code's
  matrix-keyed `ORDINAL` lookup that collapses the double fibre.
- **The `1 − max` image rule (`05 §4.5`)** is implemented literally, with the cuboid image per world
  axis; `apply(Cuboid)` returns `null` off-lattice rather than clamping.
- **`Heading.step()`, `opposite()`, `axis()`** and `Turn` order-4 arithmetic: the doc's step vectors
  are the code's constants.
- **`ReadStatus` (`06 §4.1`).** Five constants in the doc's order plus the single `readable()`
  predicate; nothing else was invented on that type.
- **`OccupantSnapshot`'s validation (`06 §3.2`).** Every documented rejection exists verbatim:
  ref/descriptor disagreement, empty footprint, `NESTED` without a child; `air(...)` is kind
  `BLOCK`, one cell, no traits.
- **Multi-cell occupants (`06 §4.3`).** `SectionSnapshot.CellIndex.elements` dedups by `ref`, drops
  air, and sorts by `ref` anchor then type then kind — the doc's "one entry per occupant … in
  `OccupantRef` order" with the order the doc names in `06 §3.1`.
- **`Locus` invariants (`05 §4.7` L-1).** `DEFINITION ⇒ source != null`, `KEY ⇒ key != null,
  cells empty, no span` are constructor checks, exactly as written.
