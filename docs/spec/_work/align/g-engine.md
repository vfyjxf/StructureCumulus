## 3. Rulings needed

1. **G9 — may `check` publish the tier frame?** (`22` §16.1 item 8, undecided)
   - (a) `check` publishes nothing; `Retention.CONTEXT` becomes a `settle`-only write and the tier frame is created at settlement. Cheapest for purity (`11` §1/P-1 hold as written); a preview loses the published context a later stage reads.
   - (b) `Retention.CONTEXT` is redefined as a write and `check` keeps publishing; `11` §1 must stop calling `check` a non-writer and `MatchOutcome`/`Spend` determinism gets a mutable store in its input tuple.
   - (c) Split: `check` publishes only when the caller asks (`check(request, publishContext)`), which reintroduces a request field `23` §7 just removed.
   Recommendation: **(a)** — it keeps `check` a pure function of `(blueprint, snapshot, siting, policy, frozen ledger)`, which is the premise of P-1 and of "a preview can never invalidate a plan".
2. **G10 — who may re-emit a `Formed`?** (spec contradicts itself: `01` §I/`22` §10.4 "only `settle` produces `Formed`" vs `11` §4.6 "the previous `Formed` is re-emitted with `generation + 1`")
   - (a) Re-emission is a second sealed arm (e.g. `MatchResult.Reemitted(Stage, Formed previous, long generation, FindingBundle)`) produced by the scheduler's liveness path, never by `check`; `Formed` stays settle-only. Recommended.
   - (b) Keep `Formed` for the re-emission but move the act to the scheduler and say so in `11` §4.6; `check` still never returns it.
   - (c) Drop re-emission entirely and let `Undecided(DIRTY_UNSTABLE)` carry `@Nullable MatchOutcome partial` with the previous claims.
   Recommendation: **(a)** — it is the only option that leaves "only `settle` produces `Formed`" true and gives the re-emission a carrier a consumer can switch on.
3. **G11 — one `UndecidedReason` set.**
   - (a) Grow `01` §I to the union of every constant any unit uses (`+ LEDGER_UNAVAILABLE, CANCELLED, UNREADABLE, ABSTAINED, NO_STEPS, NO_JUDGING_UNIT`), and re-issue `11` §4.4's precedence over that set. Recommended, with the caveat that `NO_STEPS` and `NO_JUDGING_UNIT` are one condition.
   - (b) Shrink to `01` §I's eight: delete `Undecided(CANCELLED)` from `04` §8 / `07` §309 and rewrite `11` §4.1/§4.4 to use `DESIGN_DEFECT`/`SUBJECT_ABSENT`. Loses the cancelled/abstained distinction `04` §8 leans on.
   - (c) Two types: `UndecidedReason` (why the engine stopped) and a separate `FoldGap` (what the units could not decide), with `Undecided` carrying both.
   Recommendation: **(a)** — the terms already appear across four unit files; renaming them is a bigger blast radius than adding rows to one glossary table.
4. **G12 — is there a prescreen at all, and who owns it?**
   - (a) Delete `PrescreenIndex`/`AnchorCandidate`/`Fingerprint`/`Census` from `11` §1/§2/§4.1/§4.3 and make bounds/anchor/census ordinary `Check`/`Focus` units per `22` §7.1; P-3 and F-1 are restated over those units. Recommended — `22` §7.1 is the newer model and the code already has no prescreen.
   - (b) Keep the four types as real U7 types and add their definitions to `01` §I (`PrescreenIndex.find`, `Census` folds, `Fingerprint` digest) so a regenerator can write §4.1's call site.
   - (c) Keep the §4.3 rules but name them as engine-internal steps with no types (`reads+bounds check before the plan runs`), which is what the code's absence implies.
5. **G7 side question — the request builder.** `01` §I says `MatchRequest` is "built with a fluent builder"; `11` §3 and `22` §9.1 show a nine-component record with no builder, and the code has none. Either add the builder to `11` §3's sketch or delete the sentence from `01` §I. (Recommend: delete the sentence — nine components in a fixed order is already deterministic, and a builder invites an unset field.)

## 4. Documentation gaps that block regeneration

**Undocumented behaviour (code has it, no spec sentence — a regenerator loses it)**

- `MatchResult` interface member is named `bundle()`, not the spec's `findings()`; and `Formed.stage()` is derived from `outcome.stage()` rather than stored (G6).
- `MatchRequest.withStage(Stage)` and `MatchRequest.retryToken()` (`MatchRequest.java:41,47`) exist nowhere in `01`/`11`/`22`; `retryToken()` fabricates a `RetryToken(ticket.next(), stage)`, which is a second producer of retry tokens beside the arms' own tokens.
- `MatchSession` exposes only `run()` (`MatchSession.java:122`); `11` §3 promises `spend()`, `remaining()`, `readSet()`, `probe()`, and `01` §I says it is "exposed to extensions only through `ProbeSession`" — no `ProbeSession` type exists in `src/` at all (grep empty).
- `InstanceBudget.remaining()` and `tryCharge(Spend)` overload are undocumented members.
- `MatchPolicy.of(int, CacheMode, boolean)` is a public widening constructor while `11` §3 says "a host may only narrow"; `MatchPolicy`'s own comment says "No field of this record is read yet".
- `MatchSession` runs aggregate computations in `plan.computations()` declaration order (`MatchSession.java:164-172`); `11` §4.1 step 3 / `22` §7.1 require Kahn order over `inputs()`. Whether `CheckPlan` already returns them Kahn-ordered is a U5 fact I could not read from this slice — flagging rather than ruling.
- `MatchSession` charges `charge(0L, 0)` for an aggregate (matching `11` §4.6 "an aggregate charges nothing") but still calls `tryCharge`, so a zero-leg aggregate can never be refused — consistent, just unstated.

**Unimplementable spec (a name/member with no definition, blocks regeneration even with no code present)**

Either define `ReadSet` + its producer or drop the member.
- `ClaimPlanner.Derived` (G5) — referenced in `11` §4.1 with `.rows()` and `.staticFootprint()`, never defined; `overlaps` in `01` §F has no type.
- `BlueprintId` (G13).
- `SeamBinding`, `InvalidationIndex`, `InstanceRef`, `ReadSet`, `CacheKey`, `CachedUnit`, `AttemptCache` — `01` §I gives rows to all seven and `11` §1/§4.6/§4.7/§5 use them, but none exists in `src/kernel/java` (`CacheMode`'s comment: "Nothing reads this and no attempt cache exists yet"), and `01` §I's `ChangeSet` shape `(Set<LatticeKey> changed, Set<ChunkKey> chunks, Set<NamespacedId> changedTypes, long revision)` differs from the code's `kernel.occupant.ChangeSet` `(cells, sections, payloads, entities, keys, revision)`. A regenerator following `01` §I produces seven types with no producers and a `ChangeSet` that matches no caller.
- `InstanceRecord` (20 §4.1/§4.3): "`InstanceRecord` is the only owner of a capture for the instance's lifetime", `SnapshotLease` "one owner: `InstanceRecord`". The code's `InstanceRecord` holds `id`, `generation`, `previous` and nothing else — no lease reference, no `of(id, lease)` factory. The ownership rule has no carrier, so P-7 (`20` §8) cannot be written.
- `20` §6.4 "`Spend` is a sum of four counters", §7 "X15 … the same `Spend` on all four legs" — `Spend` is two legs by `11` §4.1, `22` §9.5 and the code (`Spend.java` `(int cells, int sections)`); the "four counters"/"four legs" wording in `20` is a leftover and must be corrected to two before `20` is used alone.

**Package/unit mismatch (`00` §5 vs the tree)**

- `01` §B is headed "U0 — base (`kernel.base`)" and lists `Budget` and `Spend` there; `00` §5's U0 row says "What are ids, budgets, cancellation and stability?". A regenerated tree would put both in `kernel.base`; a tree that keeps them in `kernel.engine` must amend `01` §B (and `11` §2's "`Spend` is a work-unit value (`20` §7)" line, which is compatible with either).
